# petal-components-mcp

An MCP server that exposes [petal_components](https://github.com/petalframework/petal_components) — the Shadcn-style component library for Phoenix LiveView — to AI coding assistants (Claude Code, Cursor, Windsurf, etc).

Without this, AI agents writing HEEx invent raw Tailwind soup and never reach for the library's components (plain HEEx tags such as `<.button>`, `<.modal>` and `<.table>`; the `pc-` prefix is only for CSS classes). With it, the AI gets the full schema for every component on demand (attrs, slots and their attrs, defaults, allowed values, usage examples) and writes idiomatic petal_components markup by default.

## Install (Claude Code)

```sh
claude mcp add petal --transport http https://mcp.petal.build/mcp
```

Then in any Phoenix project, ask the AI to build something. It'll call `list_components` and `get_component` to ground its output in real petal_components schemas.

## Available tools

- `get_install_instructions` - step-by-step install for a Phoenix project (dep, Tailwind v4 CSS, `use PetalComponents`, JS hooks), plus an optional step that syncs the petal_components usage rules into `CLAUDE.md` or `AGENTS.md` via [usage_rules](https://hexdocs.pm/usage_rules)
- `list_components` - every component in the library with a one-line summary
- `get_component` - full schema (attrs, slots and slot attrs, defaults, values, docs) + HEEx usage example. Responses say when the HEEx needs an alias (`alias PetalComponents.Chat`, `alias PetalComponents.DataTable.{State, Engine}`) and mark examples that call the library's showcase demo data. Private helper functions (`defp`) are not served.

Coming soon: `search_components` (natural-language match) and `generate_pattern` (composed blocks like form-in-card, modal-with-form, dashboard skeletons).

## How it works

The MCP server is a thin TypeScript service that bundles a JSON snapshot of every component in `petal_components`. The JSON is generated by a Mix task that introspects `Phoenix.Component.__components__/0` on every loaded `PetalComponents.*` module, so nothing is duplicated by hand. The snapshot is not refreshed automatically: after each petal_components release someone runs the sync below and deploys. A daily GitHub Action (`schema-sync-check.yml`) fails when the live server's version differs from the latest release on Hex.

```
petal_components (Hex)              petal-components-mcp (this repo)
       │                                       │
       │ mix run extract_schemas.exs           │
       │─────────────────────────────────────► src/schemas.json
                                               │
                                               │ tsc
                                               ▼
                                         dist/server.js  ◄── deployed to Fly
```

## Running locally

```sh
# Regenerate schemas from the petal_components version pinned in scripts/extract/mix.lock
npm run extract     # cd scripts/extract && mix deps.get && mix run extract_schemas.exs

# Build, test and serve
npm ci
npm run build
npm test
PORT=8765 npm start

# Health check
curl http://localhost:8765/healthz
```

The extraction is self-contained — `scripts/extract/` is a tiny Mix project that pulls `petal_components` from Hex, introspects every `Phoenix.Component.__components__/0`, and writes `src/schemas.json`. No need for a local `petal_components` clone.

To use a local server with Claude Code:

```sh
claude mcp add petal-local --transport http http://localhost:8765/mcp
```

## Deploy (Fly.io)

The MCP server is hosted at `mcp.petal.build` on Fly.io as a standalone app.

### First-time setup

```sh
# 1. Create the app (one-time, requires Fly auth)
fly apps create petal-components-mcp

# 2. Deploy
fly deploy --remote-only

# 3. Add the custom domain
fly certs add mcp.petal.build
```

After step 3, Fly prints the DNS records you need. Add a CNAME at the petal.build DNS provider:

```
mcp.petal.build  CNAME  petal-components-mcp.fly.dev
```

Then `fly certs check mcp.petal.build` will go green once propagation hits.

### Subsequent deploys

```sh
fly deploy --remote-only
```

### Syncing after a new petal_components release on Hex

```sh
# 1. Move the extract's pin to the new release. The extract has its own
#    mix.lock; skip this and the server keeps the old version.
(cd scripts/extract && mix deps.update petal_components)

# 2. Regenerate schemas from the pinned version
npm run extract

# 3. Eyeball the diff (catches surprises before they ship to AI agents worldwide)
git diff src/schemas.json | head -50

# 4. Run the tests against the new snapshot
npm test

# 5. Commit and deploy
git add scripts/extract/mix.lock src/schemas.json
git commit -m "chore: sync schemas with petal_components vX.Y.Z"
git push
fly deploy --remote-only
```

The `/healthz` endpoint reports the bundled version, so you can confirm a deploy went out:

```sh
curl https://mcp.petal.build/healthz
# {"ok":true,"petal_components_version":"4.18.0","components":190,...}
```
